# Security policy

## Supported versions

The latest release is the supported version. Security fixes land on `main` and ship in the next tagged release. There are no long-term-support branches; older tags stop receiving updates once a newer release exists. See [SUPPORT.md](SUPPORT.md) for the full support scope.

| Version | Supported |
|---|---|
| Latest release | Yes |
| Older releases | No (upgrade to latest) |

## Reporting a vulnerability

Report vulnerabilities privately through [GitHub private vulnerability reporting](https://github.com/GRodolphe/PouetHugo/security/advisories/new) on this repository. Do not open a public issue for a security problem.

Our coordinated disclosure process:

- **Acknowledgement**: within 7 days of your report.
- **Assessment and triage**: within 14 days we confirm the issue and give you an expected fix timeline.
- **Disclosure**: we aim to fix and publicly disclose within 90 days of the initial report. We coordinate the timing with you, and can extend the window when a fix is genuinely in progress.
- **Publication**: confirmed vulnerabilities are published as [GitHub Security Advisories](https://github.com/GRodolphe/PouetHugo/security/advisories) with a CVE where warranted, so users have a public record.

If you would prefer to encrypt your report or reach a maintainer directly, use the contact in [GOVERNANCE.md](GOVERNANCE.md).

## Vulnerability management policy

- **Dependencies (SCA).** Dependencies are tracked with npm plus a committed `package-lock.json`, and monitored by Dependabot. Any dependency advisory rated **high or critical** is remediated before the next release; moderate and low are addressed on a best-effort basis. A pull request that would introduce a known-vulnerable dependency is flagged automatically by the [dependency-review workflow](.github/workflows/dependency-review.yml) and must be resolved before merge.
- **Code (SAST).** Every pull request and the default branch are scanned by [CodeQL](.github/workflows/codeql.yml). Any **high or critical** finding is remediated before the next release; lower-severity findings are triaged and tracked.
- **Coverage.** Non-exploitable findings are recorded in the project's [VEX document](docs/vex.openvex.json) so consumers can distinguish "not affected" from "unpatched".

## Release integrity and provenance (SLSA Build Level 3)

Every release tag publishes a source archive and a CycloneDX SBOM, each with [SLSA v1.0 Build Level 3](https://slsa.dev/spec/v1.0/levels) provenance generated by the isolated, reusable [slsa-github-generator](https://github.com/slsa-framework/slsa-github-generator) workflow. The provenance file (`*.intoto.jsonl`) is attached to the GitHub release next to the assets.

To verify an archive before using it:

```bash
# https://github.com/slsa-framework/slsa-verifier
slsa-verifier verify-artifact pouethugo-v1.0.0.tar.gz \
  --provenance-path pouethugo-v1.0.0.tar.gz.intoto.jsonl \
  --source-uri github.com/GRodolphe/PouetHugo \
  --source-tag v1.0.0
```

A valid result proves the archive was built by this repository's release workflow on GitHub-hosted runners from the stated tag, and was not tampered with afterwards.

## Scope notes for template users

- The template ships no server-side code; the attack surface of a deployed site is your host plus the runtime origins listed in [docs/security-model.md](docs/security-model.md) (Google Fonts, jsdelivr at pinned versions, and analytics only if you enable it).
- `markup.goldmark.renderer.unsafe = true` allows raw HTML in markdown. That is safe while you are the only author; reconsider it if untrusted contributors can commit content. See the threat model in [docs/security-model.md](docs/security-model.md).
